## 1. Grammar

### 1.1 Notation

We use EBNF with the following conventions:

- `::=` means “is defined as”.
- `|` separates alternatives.
- `{ ... }` means zero or more repetitions.
- `[ ... ]` means optional.
- `( ... )` groups alternatives.
- `X+` means one or more repetitions of `X`, equivalent to `X { X }`.
- `"..."` denotes a terminal token.
- Juxtaposition means concatenation.

The language generated by this grammar is the set of all valid programs: a sequence of zero or more relation definitions followed by exactly one query.

### 1.2 Token classes (lexical grammar)

The tokenizer produces the following token kinds.

```
letter        ::= "A".."Z" | "a".."z" | "_"
digit         ::= "0".."9"
ident         ::= letter { letter | digit }
integer       ::= [ "-" ] digit { digit }
string        ::= "'" { string_char | "''" } "'"
string_char   ::= any character except "'"
bare_string   ::= bare_char { bare_char }
bare_char     ::= any character except "," | " " | "\t" | "\n" | "\r" | "(" | ")" | "{" | "}" | "'"
keyword       ::= "select" | "project" | "rename"
                | "union" | "intersect" | "minus" | "times" | "join"
                | "and" | "or" | "not"
symbol        ::= "(" | ")" | "[" | "]" | "{" | "}"
                | "," | "." | "=" | "!=" | "<" | "<=" | ">" | ">="
newline       ::= "\n"
comment       ::= "//" { any character except newline }
```

Whitespace other than newline is skipped. Comments are skipped, but the newline that ends the comment is **not** consumed by the comment rule; it is tokenized separately as a `Newline` token. A comment may appear at the end of the file with no trailing newline.

Every token carries its character position in the input for error reporting.

The tokenizer implements **maximal munch**: on seeing `>` it checks the next character before deciding whether the token is `>` or `>=`. On seeing `<` it checks before deciding `<` or `<=`. On seeing `!` it checks before deciding `!=`. If a `!` is not immediately followed by `=`, that is a lexical error. On seeing `-` it checks before deciding whether the token is a negative integer literal or a lexical error (see 1.3).

### 1.3 Integer literals

The tokenizer recognises a leading `-` as the start of an integer literal **only when it is immediately followed by a digit**. There is no unary minus operator in the language. A `-` that is not immediately followed by a digit is a lexical error.

Documented semantics:

- **Leading zeros.** Allowed. `007` denotes 7. `-007` denotes −7. The language has no octal or hexadecimal literals; all integer literals are decimal.
- **Range.** An integer literal must lie in the signed 64-bit range [−9223372036854775808, 9223372036854775807]. A literal outside this range is a lexical error reported at the position of the literal.
- **Unary minus.** There is no unary minus operator. The minus sign is part of the literal. `select[Age>-30](R)` produces the tokens `select`, `[`, `Age`, `>`, `-30`, `]`, `(`, `R`, `)`. A space between `-` and the digits, as in `- 30`, produces a lone `-` token, which is a lexical error.

### 1.4 String literals

A string literal is written in single quotes. Inside a quoted string, two single quotes `''` stand for one literal single quote character. There are no backslash escapes. A string may span multiple lines. An unterminated string is a lexical error reported at the position of the opening quote.

Examples:

- `'Bob)'` is the four character string `Bob)`.
- `'a,b'` is the three character string `a,b`.
- `'O''Brien'` is the seven character string `O'Brien`.

### 1.5 Identifiers, keywords, and bare strings

Identifiers are spelled with letters, digits and underscore, and must begin with a letter or underscore.

The keywords are `select`, `project`, `rename`, `union`, `intersect`, `minus`, `times`, `join`, `and`, `or`, `not`.

**Rule.** A keyword token is treated as an identifier whenever the grammar expects an `IdentLike` at that position. Otherwise it is treated as its keyword role. Concretely, this means:

- `select[union=3](R)` is legal; `union` is an attribute name here.
- `project[Name](select[Age>30](Employees))` still works; the `select` tokens are in keyword positions.
- A relation may be named after a keyword, for example `join(R)` is a valid relation definition name.

**Lexical categories in operand position.** The distinction between an attribute reference and a string literal is made by quoting:

- A bare token such as `x` or `Emp.DID` in operand position is an **attribute reference**.
- A single-quoted token such as `'x'` in operand position is a **string literal**.

So `select[A=B](R)` compares the attribute `A` with the attribute `B`. `select[A='B'](R)` compares the attribute `A` with the string `B`.

**Lexical categories in tuple-value position.** Inside a relation definition tuple, a bare token that is not a valid integer is a **string value**. For the purposes of this grammar, a bare string value must be a valid identifier or keyword (i.e. it must match `IdentLike`). Any string that contains a comma, a space, a parenthesis, or a quote character must be quoted with single quotes.

**Bare tuple values.** In tuple-value position, a bare token that is not a valid integer is a string value. It may contain any character except a comma, whitespace, parentheses, braces, a single quote, or the two-character sequence `//`. For example, `E-1`, `1a`, and `foo-bar` are valid bare strings. If a value contains a comma, space, parenthesis, quote, or `//`, it must be quoted with single quotes.

### 1.6 Newlines and comments

A comment begins with `//` anywhere outside a quoted string and runs to the end of the line. Blank lines are ignored.

A newline is tokenized as a `Newline` token. The parser treats `Newline` as whitespace in all contexts **except** inside a `TupleList`, where newlines separate tuples. Inside a `TupleList`, the parser follows this algorithm:

1. Skip any leading `Newline` tokens. If the next token is `}`, the tuple list is empty and we are done.
2. Parse a tuple with the following sub-algorithm:
    1. Parse a `TupleValue`.
    2. Loop: tentatively skip any consecutive `Newline` tokens. If the next token is `,`, keep the skipped newlines as intra-tuple whitespace, consume the `,`, skip any consecutive `Newline` tokens, parse another `TupleValue`, and repeat. Otherwise, restore the parser position to the point just after the previous value, and leave the loop. The skipped newlines were **not** consumed and are still available to the tuple-separator step.
        
3. After the tuple has been parsed, if the next token is `}`, the tuple list ends.
4. Otherwise, the next token must be at least one `Newline`. Consume all consecutive `Newline` tokens. If the next token is `}`, the tuple list ends. Otherwise, go back to step 2 to parse the next tuple.

The key point is that a run of newlines after the last value of a tuple is only consumed as intra-tuple whitespace if it is followed by a comma. Otherwise those newlines are left in the token stream for the tuple-separator step, which requires them.

### 1.7 Syntactic grammar

```
Program          ::= { RelationDef } Query
RelationDef      ::= IdentLike "(" AttrNameList ")" "=" "{" TupleList "}"
AttrNameList     ::= AttrName { "," AttrName }
AttrName         ::= IdentLike
TupleList        ::= [ Newline+ ] [ Tuple { Newline+ Tuple } ] [ Newline+ ]
Tuple            ::= TupleValue { { Newline } "," { Newline } TupleValue }
TupleValue       ::= Integer | String | BareString
Query            ::= Expr
Expr             ::= SetExpr
SetExpr          ::= IntersectExpr { ( "union" | "minus" ) IntersectExpr }
IntersectExpr    ::= TimesJoinExpr { "intersect" TimesJoinExpr }
TimesJoinExpr    ::= UnaryExpr { ( "times" | "join" "[" Condition "]" ) UnaryExpr }
UnaryExpr        ::= "select" "[" Condition "]" "(" Expr ")"
                   | "project" "[" AttrList "]" "(" Expr ")"
                   | "rename" "[" IdentLike "]" "(" Expr ")"
                   | "(" Expr ")"
                   | IdentLike
AttrList         ::= Attr { "," Attr }
Attr             ::= IdentLike
Condition        ::= OrCondition
OrCondition      ::= AndCondition { "or" AndCondition }
AndCondition     ::= NotCondition { "and" NotCondition }
NotCondition     ::= "not" NotCondition | PrimaryCondition
PrimaryCondition ::= "(" Condition ")" | Comparison
Comparison       ::= Operand CompOp Operand
CompOp           ::= "=" | "!=" | "<" | "<=" | ">" | ">="
Operand          ::= Integer | String | AttrRef
AttrRef          ::= IdentLike [ "." IdentLike ]
IdentLike        ::= ident | "select" | "project" | "rename"
                   | "union" | "intersect" | "minus" | "times" | "join"
                   | "and" | "or" | "not"
```

Notes on the grammar:

- `project[]` is a syntax error because `AttrList` requires at least one `Attr`.
- `project[Name, Name]` is syntactically valid but is a semantic error; see Section 5.2.
- `select[not=3](R)` is legal: `not` is an `IdentLike` in operand position, so it is an attribute reference. See Section 4 for how the parser resolves the keyword/identifier choice.
- `select[not (a=1) or b=2](R)` is legal: `not` here is the keyword operator.

## 2. Precedence and associativity

### 2.1 Expression operators

Highest precedence at the top.

|Level|Operators|Associativity|Grammar rule|
|---|---|---|---|
|1|`select`, `project`, `rename`, parentheses|—|`UnaryExpr`|
|2|`times`, `join`|left|`TimesJoinExpr`|
|3|`intersect`|left|`IntersectExpr`|
|4|`union`, `minus`|left|`SetExpr`|

Consequences:

- `A union B minus C` parses as `(A union B) minus C`.
- `A minus B minus C` parses as `(A minus B) minus C`.
- `A times B intersect C` parses as `(A times B) intersect C`.
- `A join[c] B times C` parses as `(A join[c] B) times C`.

### 2.2 Condition operators

Highest precedence at the top.

|Level|Operators|Associativity|Grammar rule|
|---|---|---|---|
|1|comparison `= != < <= > >=`|non-associative|`Comparison`|
|2|`not`|right|`NotCondition`|
|3|`and`|left|`AndCondition`|
|4|`or`|left|`OrCondition`|

Consequences:

- `not (a=1 and b=2) or c>3` parses as `(not (a=1 and b=2)) or (c>3)`.
- `a=1 and b=2 or c=3` parses as `(a=1 and b=2) or (c=3)`.
- Comparisons do not chain. `a = b = c` is a syntax error.

## 3. Ambiguity demonstration

### 3.1 The naïve grammar

Consider the deliberately naïve grammar:

```
Expr ::= Expr "union" Expr
       | Expr "minus" Expr
       | "(" Expr ")"
       | IDENT
```

For the input `A union B minus C`, this grammar is ambiguous. It admits two different parse trees.

### 3.2 Two parse trees for `A union B minus C`

**Tree 1: `(A union B) minus C`**

```
      minus
     /     \
  union     C
 /     \
A       B
```

**Tree 2: `A union (B minus C)`**

```
      union
     /     \
    A     minus
         /     \
        B       C
```

### 3.3 A concrete instance where they differ

Let the three relations have a single attribute `x`:

- `A(x) = {1}`
- `B(x) = {2}`
- `C(x) = {1}`

Tree 1 evaluates as:

```
(A union B) minus C
= ({1} union {2}) minus {1}
= {1,2} minus {1}
= {2}
```

Tree 2 evaluates as:

```
A union (B minus C)
= {1} union ({2} minus {1})
= {1} union {2}
= {1,2}
```

The two trees produce different results, so the naïve grammar is ambiguous in a way that matters.

### 3.4 The stratified grammar that removes the ambiguity

The grammar in Section 1.7 removes the ambiguity by stratifying expressions into precedence levels:
```
SetExpr       ::= IntersectExpr { ( "union" | "minus" ) IntersectExpr }
IntersectExpr ::= TimesJoinExpr { "intersect" TimesJoinExpr }
TimesJoinExpr ::= UnaryExpr { ( "times" | "join" "[" Condition "]" ) UnaryExpr }
```

Because `union` and `minus` are in the same level, and the repetition `{ ... }` is implemented as a left-associative loop, the only derivable parse of `A union B minus C` is:

```(A union B) minus C```

That is Tree 1. Tree 2 is no longer derivable from the stratified grammar, because after parsing `A union B` the parser is at the `SetExpr` loop and the next token `minus` is consumed as a second `( "union" | "minus" )` iteration, producing a left-associative tree.

### 3.5 Associativity of `minus`

For `A minus B minus C`, the grammar forces left associativity:
`(A minus B) minus C`. The right-associative grouping `A minus (B minus C)`
gives a different result in general.

Example with single-attribute relations `x`:

- `A(x) = {1, 2}`
- `B(x) = {2}`
- `C(x) = {1}`

Left grouping:
```
(A minus B) minus C  
= ({1,2} minus {2}) minus {1}  
= {1} minus {1}  
= {}
```

Right grouping:
```
A minus (B minus C)  
= {1,2} minus ({2} minus {1})  
= {1,2} minus {2}  
= {1}
```
## 4. Parsing strategy justification

We use a hand-written recursive descent parser with one token of lookahead for expressions. The tuple-list parser uses bounded backtracking over runs of `Newline`.

Recursive descent cannot handle left recursion directly. A rule such as:

`Expr ::= Expr "union" Expr`

would cause infinite recursion, because the parser would try to parse an `Expr` by first parsing an `Expr`.

We avoid left recursion by stratifying the expression grammar into levels and using iteration instead of left recursion. For example, `SetExpr` is written as:

`SetExpr ::= IntersectExpr { ( "union" | "minus" ) IntersectExpr }`

The parser implements this as: parse an `IntersectExpr`; then, in a `while` loop, while the next token is `union` or `minus`, consume it, parse another `IntersectExpr`, and build a left-associative node. The same technique is used for `IntersectExpr`, `TimesJoinExpr`, `OrCondition` and `AndCondition`.

**Left recursion that was removed.** The naïve rule `Expr ::= Expr "union" Expr` was replaced by the stratified `SetExpr` rule above. The naïve rule `Expr ::= Expr "minus" Expr` was replaced by the same rule. The naïve condition rules `OrCondition ::= OrCondition "or" AndCondition` and `AndCondition ::= AndCondition "and" NotCondition` were replaced by the iterative forms in Section 1.7.

**Keywords as identifiers.** Because keywords are allowed as identifiers (Section 1.5), the parser sometimes has to decide whether a token such as `not` is the keyword operator or an attribute reference. This decision is made with one token of lookahead:

- At the start of a `NotCondition`, if the next token after `not` is `=`, `!=`, `<`, `<=`, `>`, `>=`, or `.`, then `not` is an operand (an attribute reference, possibly qualified). Otherwise `not` is the keyword operator.
- At the start of a `UnaryExpr`, `select`, `project`, or `rename` is the keyword operator if and only if the next token is `[`. Otherwise it is an `IdentLike` (a relation name).
- Elsewhere, the grammar position determines the role. For example, after a complete `Comparison`, the only valid continuations are `and`, `or` and the end of the condition, so an `and` or `or` token there is the keyword operator. At the start of a `Comparison`, an `and` or `or` token is an operand.

This gives a deterministic parser for every input generated by the grammar.

## 5. Semantic rules documented for completeness

The following rules are not part of the grammar; they are checked during evaluation. They are listed here because several of them are also mentioned in the tokenizer and parser sections.

### 5.1 Duplicate attribute names in a relation definition

A relation definition `R(a, a) = { ... }` is a semantic error: attribute names within a relation must be distinct.

### 5.2 Duplicate attributes in a projection

`project[Name, Name](R)` is a semantic error. The project description calls this case out as “Decide and document”, and because it is not given a definite meaning, we reject it with a clear message rather than silently collapsing or keeping duplicates.

### 5.3 Union compatibility

`union`, `intersect` and `minus` require the two inputs to be union compatible: the same number of attributes, the same attribute names in the same order, and compatible types position by position. Anything else is a semantic error.

### 5.4 Type compatibility in comparisons

A comparison between a number and a string is a semantic error, not a silent false. Comparisons between two numbers are ordered; comparisons between two strings are ordered lexicographically; equality and inequality are defined for both.

### 5.5 Qualified-name resolution

A qualified name `R.A` is resolved against the schema of the relation currently named `R` in scope. If `R` is not in scope, or `A` is not an attribute of `R`, that is a name error. An unqualified name `A` is resolved against the union of the attributes in scope; if it is ambiguous (for example after a `times` that left two attributes called `A`), that is a name error.

**Collision after `times`.** The `times` operator combines the attributes of both inputs, qualified by relation name. If both inputs contain a relation with the same name (for example, after a `times` without a preceding `rename`), then any qualified reference `R.A` where `R` is the duplicated name is ambiguous and is a name error. This is exactly why `rename` is necessary for self joins: without renaming one side, both sides carry the same relation name and the qualified names cannot be distinguished.

### 5.6 Projection duplicate removal

`project[attrs](R)` returns the listed attributes in the listed order, then
removes duplicate tuples. The result is a set of tuples, so duplicate rows
collapse to one. This is required by the assignment’s semantics for `project`.
